# 최적화 후보 찾기 (2026-10-23)

측정 환경: 로컬 서버(localhost:8756)에서 브라우저 창에 v7.0.0 + 7.1 작업분을 열고 `performance`·`performance.now()`로 쟀다. **내 PC 한 대 값**이라 휴대폰·저사양에서는 더 느리다. 코드는 건드리지 않았다.

## 1. 전투 중 UI 갱신 (가장 큼)

- `loop()`는 화면이 갱신될 때마다(60~120번/초) `update()`를 한 번 부르고, `update()` 끝에서 `render()`를 부른다. 모든 유닛·전투 계산을 다 합쳐도 한 프레임 5ms 안팎인데 그중 **`render()`가 4.0ms**다. 같은 전투를 레전드 40장(적 50마리)에서 재도 96%가 `render()`였다(전체 4.9초 중 4.9초).
- `render()` 안에서 비싼 것(프레임당): `renderNewButtons` **2.09ms**, `renderUnitLevels` 1.23ms, `renderDeckButtons` 1.02ms. 이들이 `allyUnlocked`를 **프레임당 약 228번**, `unitStats`를 **약 335번** 부른다(애드온이 여러 겹으로 감싸서 한 번 부를 때마다 비용이 크다).
- 원인: 아군 버튼이 115개 만들어져 있고(덱에 없는 것도) 매 프레임 전부 다시 계산·갱신한다. 돈·쿨다운 값은 같아도 매번 같은 텍스트·스타일을 다시 쓴다.
- 해결 방향(조합 가능):
  1. 덱에 있는 버튼만 갱신(덱 밖 버튼은 화면에 안 보임).
  2. UI 갱신을 초당 10~15번으로 제한(쿨다운 막대는 부드럽게 보이도록 보간하거나 15Hz로).
  3. `allyUnlocked`·`unitStats`·`unitCost`를 프레임 단위로 캐시(레벨·보물·클리어 변경 때만 무효화).
  4. 값이 바뀔 때만 DOM에 쓰기(이전 값 비교).
- 기대: 프레임당 4ms → 0.5ms 이하. 60Hz 기준 이 PC에서도 초당 약 0.24초(24%)를 쓰던 것을 줄이고, 120Hz·휴대폰에서 가장 체감된다.
- 위험: 쿨다운·돈 표시가 한 박자 늦어 보일 수 있고, 버튼 비활성 조건(돈·출격 한도)을 놓치면 눌러야 하는 순간에 안 눌릴 수 있다. 시험이 필요하다(버튼 상태 비교 시험).

## 2. 스크립트 59개 · JS 1.36MB

- 첫 로딩 요청 68개 중 JS가 59개, 1,358KB. `game.js` 795KB, `zombie-outbreak-data.js` 67KB, `cosmos2-data.js` 57KB.
- 로컬에서는 로딩 97ms지만 GitHub Pages·모바일에서는 요청 수와 크기가 더 크게 보인다(요청마다 왕복 지연).
- 해결: 순서를 지키는 병합 + 최소화. 애드온이 `game.js`의 함수를 덮어쓰는 구조라 **로딩 순서를 바꾸면 안 된다**(병합해도 같은 순서 유지). 캐시 번호(`?v=`) 관리 방식도 바꿔야 한다.
- 위험: 중간. 병합 후 모든 기존 시험(스크립트 로딩 순서에 의존)을 다시 돌려야 한다.

## 3. 배포에 들어가는 안 쓰는 자산

- 코드·html·css 어디에서도 참조하지 않는 이미지 53개, **30MB**. 대부분 컨셉 그림(플래티넘·코랄 3진·크리스프·라바 3진)과 `Gold.png` 2.2MB, `ivory.png` 1.8MB.
- 플레이어가 받지는 않지만(참조가 없어서) 저장소와 Pages 배포 크기를 키운다.
- 해결: `work/` 같은 배포 제외 위치로 옮기기. 위험 낮음.

## 4. 큰 보스 시트

- 이미지는 필요할 때만 받는다(시험에서 전투 몇 번에 22개, 963KB). 다만 처음 만나는 보스는 한 번에 크다: `boss_nyandam_attack.webp` 2.6MB, `boss_magpie` 1.9MB, `anim_kamisama` 1.7MB, `anim_kamisamaserious` 1.7MB, `anim_alienbunbun` 1.5MB.
- 해결: 보스 입장 전 미리 받기(로딩 표시), 또는 프레임 수·화질 조정. 위험 낮음.

## 누수·기타

- 같은 스테이지를 4번 연달아 돌려도 DOM 노드 수(2,240 → 2,241)와 힙(8~9MB)이 그대로다. **누수 없음.**
- 전투 로직 자체(`update` 안의 계산)는 프레임당 0.3ms 수준으로 이미 빠르다.
- 아직 안 잰 것: 실제 휴대폰 프레임, 위키(도감) 열기 시간, 스테이지 선택 화면, 저장(localStorage) 빈도.

## 추천 순서

1. **1번(UI 갱신)** — 효과가 가장 크고 눈에 띄는 개선. 먼저 버튼 상태 비교 시험을 만든 뒤 바꾼다.
2. 3번(안 쓰는 자산 정리) — 위험이 거의 없다.
3. 2번(병합·최소화)은 1번 뒤에, 4번은 필요할 때.
