# 최적화 후보 찾기 2차 (2026-10-24)

10-23 1차(`최적화-후보-2026-10-23.md`)에서 못 잰 것(화면 여는 시간·저장 빈도·전투 전 다운로드)을 재고, v7.1.2 기준으로 1차 수치를 다시 쟀다. 코드는 건드리지 않았다.

**측정 환경:** 이 PC의 헤드리스 Chrome + 로컬 서버. 휴대폰 환산은 CPU를 4배 느리게 한 값(거친 대용치, 실기기 아님). 다운로드 시간은 10Mbps(초당 약 1.2MB) 가정. 측정 스크립트는 세션 작업 폴더(perf-probe*.cjs)에 있고 저장소에는 넣지 않았다.

## 1. 전투 전 그림 다운로드 (사용자가 가장 먼저 체감)

- 스테이지 696곳을 덱 10명(전부 처음 받는 상태)으로 계산: **중앙값 4.7MB, 90% 5.5MB, 최대 9.7MB**(냥코 카타르시스). 덱 없이 적+공용만이면 0.4MB다. 즉 거의 전부가 **아군 시트**다.
- `asset-loader.js`의 `battleImageUrls()`는 덱의 각 아군마다 `base.sheet`(1진)와 지금 쓰는 형태의 시트를 **둘 다** 받는다. 아군 107명의 시트는 형태당 평균 230KB(1진 합 24.6MB · 2진 합 24.4MB · 3진 합 7.9MB)라, 2진·3진으로 쓰는 덱이면 1진 시트 약 2.3MB는 전투에서 쓰이지 않는다.
- 해결: 쓰는 형태의 시트만 받고, 형태를 바꿀 때(훈련·도감 미리보기) 그 형태를 받는다. 전투 그림 전체는 152개 49.3MB.
- 확인한 것: 전투에서 1진 시트로 되돌아가는 곳은 `game.js` 2401번째 줄 하나뿐이고, 그것도 **쓰는 형태에 자기 시트가 없을 때**(`atlas.sheet`가 비어 있을 때)만이다. 그래서 `battleImageUrls()`가 `base.sheet`를 "쓰는 형태에 자기 시트가 없는 경우에만" 넣도록 바꾸면 된다. 도감·프로필은 전투 그림 준비와 별개다. 바꾼 뒤 7.1 그림 브라우저 시험과 형태 시험으로 확인한다.
- 참고: 큰 보스·아군 시트를 화질만 낮춰 다시 저장해 봤더니 2~14%만 줄었다(이미 손실 압축). **재압축은 효과가 작다.**

## 2. 전투 중 UI 갱신

- 한 프레임 3.0ms 중 `render()`가 2.7ms(90%). 그 안에서 `renderNewButtons` **1.37ms**, `renderUnitLevels` **1.24ms**가 97%다(1차에서 `renderDeckButtons` 1.0ms가 있었는데 지금은 0.08ms로 줄었다).
- 프레임당 호출: `allyUnlocked` 236회, `unitStats` 514회, `unitCost` 284회. 아군 버튼 DOM은 115개(덱 밖 포함)를 매 프레임 다시 계산한다.
- CPU 4배 느리게: 프레임당 25ms → 60Hz에서 40fps 아래. 화면 주사율이 120Hz인 기기는 `loop()`가 화면 갱신마다 불러서 비용이 2배로 든다.
- 해결(1차와 같음, 우선순위): ① 덱에 있는 버튼만 갱신 ② `unitStats`·`unitCost`·`allyUnlocked` 프레임 단위 캐시 ③ 값이 바뀔 때만 DOM 쓰기 ④ UI 갱신 10~15Hz로 제한.

## 3. 시작 로딩

- 첫 로딩: JS 65개 1,409KB(gzip 추정 **397KB** — GitHub Pages는 압축해서 보내므로 1차에서 말한 1.4MB보다 실제 전송은 훨씬 작다), 이미지 8개 32KB.
- 로컬 481ms 중 파싱·컴파일이 약 290ms, `game.js` 실행 131ms, `rank.js` 15ms. 휴대폰 환산 약 1.7초.
- 늦게 받아도 되는 후보(화면을 열 때만 필요): `wiki-guide`·`codex-*`·`true-form-reviews`·`ally-comparison` 약 110KB, 데이터 `zombie-outbreak-data` 69KB · `cosmos2-data` 59KB · `legend-40` 17KB. 합 약 250KB(raw)이지만 애드온이 `game.js` 함수를 덮어쓰는 구조라 순서 의존이 있어 일부만 안전하다.
- 병합·최소화는 요청 수(65개)와 파싱 시간에는 효과가 있지만, 압축 전송 기준 용량 절감은 크지 않다. 효과 대비 위험(순서 의존) 때문에 1·2번 뒤에 한다.

## 4. 저장소·배포 크기

- 추적 파일 894개 **181MB**: `assets` 150MB, `docs` 18MB(시뮬레이션 JSON 하나가 9.7MB), `reference-sheets` 8.5MB. GitHub Pages는 저장소를 그대로 배포하지만, 플레이어는 참조하는 파일만 받는다.
- 참조 없는 그림 62개 34MB(컨셉 그림이 대부분: 플래티넘 12.8MB·코랄 4.8MB·라바 3.3MB·크리스프 2.8MB·7.1 신캐 4.4MB, 그리고 `Gold.png` 2.3MB·`ivory.png` 1.9MB). 컨셉 그림은 지금까지 커밋하는 관례였지만, 크기를 줄이려면 배포 제외 위치로 옮기면 된다.
- 로컬 `.git`은 풀리지 않은 느슨한 객체가 6,701개(937MB) + 팩 228MB다. `git gc`로 줄일 수 있다(로컬 전용, 원격·플레이어와 무관). 작업 폴더에는 추적하지 않는 큰 폴더가 있다: `exports` 207MB · `work` 286MB · `reference-sheets` 156MB · `Python` 139MB(커밋하면 안 됨).

## 문제 없는 것

- 스테이지 선택 열기 약 35ms(DOM 1,416개, 카드 91개), 도감 첫 열기 14ms, 위키 8~25ms, 뽑기·덱 세팅 화면은 즉시. 처음 한 번 270ms가 나온 적이 있으나 재현되지 않았다(JIT 워밍업으로 추정).
- 저장: 전투 한 판(3,600프레임) 동안 localStorage 쓰기 0회. 저장 항목은 진행도 2.7KB 등 모두 작다.
- DOM·메모리 누수 없음(1차 측정).

## 아직 못 잰 것

- 실제 휴대폰 프레임·로딩, GitHub Pages 실사이트의 요청 지연, 120Hz 기기에서의 실제 프레임.

## 추천 순서

1. **1번(전투 전 다운로드)** — 수정 범위가 작은 편(`asset-loader.js` 조건 하나)이고 약 2MB(중앙값 −45%)가 줄며 위험이 낮다. 먼저 해 볼 만하다.
2. **2번(UI 갱신)** — 전투 중 프레임이 가장 크게 좋아진다. 버튼 상태 비교 시험을 먼저 만든다.
3. 4번(안 쓰는 그림·`git gc`) — 위험이 거의 없다.
4. 3번(시작 로딩)은 1·2번 뒤에, 5번은 필요할 때.
